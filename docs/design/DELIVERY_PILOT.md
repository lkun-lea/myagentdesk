# #11 单需求交付试点

用同一条真实 GitHub Issue 串起已确认的 OpenSpec、版本计划、候选、独立验收和发布回执。首版选择 tebb 已有的 WSL + bubblewrap 终端，工作台通过本机适配器接收证据。人确认产品范围、验收放行和发布。需求群的产品阶段仍用官方 Pi SDK。

```mermaid
flowchart LR
    I[GitHub Issue 和 OpenSpec] --> P[需求与版本计划]
    P --> D[研发派发]
    D --> T[tebb 本机沙箱]
    T --> C[固定提交和候选补丁]
    C --> A[测试成员独立复跑]
    A --> Q[质量确认并核对同提交 CI]
    Q --> R[获授权成员发布]
    R --> L[本地试点渠道和实际回执]
```

## 界面与状态

| 入口 | 操作和应显示的结果 |
| --- | --- |
| 项目时间线 | 在已承诺计划中纳入该需求，填写发版必过项。改期创建新修订。质量确认后进入等待构建放行，再进入等待发布回执。回执入档后，时间线给出渠道实际发布时间。 |
| 需求群 | 建群时选择「手动推进，使用 tebb 执行交付试点」。产品阶段结束后，研发填写已准备的完整候选 SHA。测试派发只能继承该候选。页面展开成功、失败、取消和待核对记录，并可下载研发实际回传的补丁。 |
| 构建与发布 | 展开候选、自测与独立证据，质量负责人输入该候选的 GitHub Actions 运行 ID，工作台读取 CI 来源并校验。项目所有者授予成员试点发布权限，获授权成员确认发布，随后查看文件名、提交、SHA-256 与实际时间。 |

## 执行与证据协议

- 派发冻结需求和验收版本、仓库连接、规格基准 SHA、候选 SHA、计划修订和发版必过项。责任人显式启动本机适配器，使用独立状态目录、已批准的克隆与本机命令清单。令牌仅用于该派发，服务保存其摘要。
- 适配器核对克隆源与候选祖先关系，将提交快照解包到该派发的 tebb 临时工作区，沙箱按本机清单执行。研发回传从基准到候选的实际补丁、摘要和自测，独立测试成员对同一 SHA 重新计算摘要并运行自己的清单。每次回传保留命令、环境、退出码、输出和 tebb 运行编号。
- 测试按冻结条件和发版必过项逐项交付。服务核对提交、摘要、执行者、需求与计划版本、完整用例和退出码。失败留在历史并允许新派发；源版本或阶段已经变化的回执只入历史。当前独立验收通过后，质量负责人才能在需求群确认。
- 领取绑定单一设备。同设备重试沿用 tebb 原请求编号，已结束的命令由原回执核对。适配器先写本机待回传文件，再提交回执。收到相同回执时返回此前结果，异内容报冲突，首次入档与需求群通知一起提交。无法确认的结果保持待核对，由负责人取消并显式另发。
- 构建放行验证同仓库、同 SHA、执行成功的 GitHub Actions `push` 工作流 `.github/workflows/ci.yml`，再绑定独立验收使用的候选摘要及计划修订。发布使用 `MAD_PILOT_RELEASE_ROOT` 下的隔离渠道。文件原子落盘后重读核对 SHA-256 所对应的原始内容，以渠道文件时间生成回执。重放同一发布请求返回已登记回执。

## 验收与范围

- 从同一条真实 Issue 创建需求，固定规格，承诺并调整一次计划。研发在 tebb 沙箱执行，工作台能下载实际补丁并查看自测。
- 测试成员对同一候选先失败、再独立通过，保留两次记录。自测、不同 SHA 或摘要、缺必过项、同一成员实现与验收和错误 CI 均应阻止放行。
- 获独立发布授权后在本地试点渠道写入该候选，核对文件字节、摘要、同提交 CI、发布人、计划修订和时间线时间。重复登记只保留一条，计划改为新修订后旧回执仍在历史。

本阶段接收研发已准备的 Git 提交，tebb 负责隔离执行、候选补丁与回执。tebb 开发 Agent 自动改代码、桌面配对、未领取队列同步、跨设备故障演练和部分文件续传继续由 [#14](https://github.com/lkun-lea/myagentdesk/issues/14) 扩展。多人需求集成包、生产发布渠道与回滚继续在 [#11](https://github.com/lkun-lea/myagentdesk/issues/11) 验收。
