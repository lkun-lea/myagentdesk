# OpenSpec 固定规格

对应 [#10 项目规格页](https://github.com/lkun-lea/myagentdesk/issues/10)。OpenSpec 文件留在项目 GitHub 仓库，MyAgentDesk 记录需求当时引用的仓库、完整提交 SHA、变更目录、目录树 SHA 和验收条件版本。需求历史里可以打开当时的目录和提案。产品确认更换引用后，系统创建新的需求版本。

## 界面与流转

1. 在项目的「GitHub Issues」页关联真实 Issue，再从「需求」进入「查看固定规格与验收」。也可从项目的「规格」页选择需求。
2. 产品负责人填写完整提交 SHA、OpenSpec 变更目录和逐条验收条件。建群前由项目所有者或管理员确认，建群后由当前获授权的产品负责人确认。后端通过 GitHub 核对连接仓库里的提交和目录，并在保存时重新检查权限和版本。旧页面提交冲突时，刷新后重新确认。
3. 产品确认后，需求群回到产品阶段，后续运行使用新需求版本。研发和测试的 Pi SDK 运行收到相同的固定规格与条件。测试从指定的研发候选出发，逐项记录通过或未通过及证据。质量负责人以当前版本、当前候选的独立验收为依据放行或退回。
4. 当前规格页展示「待验收」「待重新验收」「有历史通过记录，当前候选待验收」「当前候选已通过」和「未通过」。从阶段交接可直接打开对应的规格版本；规格页也可用版本选择器切换。证据可展开，包含候选运行、独立验收运行标识、结论与逐项记录。

## 变更与证据

| 产品确认的变化 | 当前需求的验收状态 |
| --- | --- |
| 更换提交，OpenSpec 目录树和需求说明相同 | 新增或改写的条件待重新验收，有过通过记录的原条件显示为历史通过，当前候选均需自己的证据 |
| 变更了 OpenSpec 目录树、来源或需求说明 | 当前条件全部待重新验收 |
| 候选运行变化 | 旧候选证据继续可查，当前候选需要独立验收 |

验收证据用需求版本、研发候选运行和测试运行定位。每项当前条件恰有一条结构化结果和证据，通过结论要求全部通过。历史需求、来源与验收记录随需求保留，查询仍受当前项目成员权限约束。未固定规格的需求沿用现有验收流程。

## 验收标准

本阶段执行结果见 [固定规格验收记录](../evals/openspec-fixed-reference-20261119.md)。

- [ ] 从一条真实 GitHub Issue 进入需求固定规格，验证提交和变更目录可打开，非完整 SHA 和不存在的目录被拒绝。
- [ ] 用研发和测试两个独立成员完成第一版交接，再更换真实提交并改写验收条件；当前需求显示受影响条件待重新验收，继承的历史结论不能放行新候选。
- [ ] 打开第一版，仍能定位其提交、原条件、候选和独立验收结果；第二版按当前条件提交新的证据后才能完成。
- [ ] 使用同一旧版本基线并发确认，只允许一次成功；撤销成员权限后，其历史链接也返回无访问权限。

本阶段使用项目已连接的公开 GitHub 仓库。活动与归档目录浏览、OpenSpec Explore 和 CLI 校验回执见 #10 的后续范围；真实候选执行器由 [#11](https://github.com/lkun-lea/myagentdesk/issues/11) 接入。
